# 服务器 Agent

「服务器 Agent」是装在你自己服务器上的一个小程序（第一版）。它按计划运行你定义的作业，记下每次运行的结果和输出，出问题时直接给你发邮件。Mac 关机或睡眠时它照常工作；PanelLab 只是遥控器，通过已固定指纹的 SSH 查看和修改它。设计依据见[设计文档](../design/design-server-agent.md)，实现与验证见[本轮记录](../project/server-agent-20261111.md)。

这里的“Agent”指服务器上的常驻进程，不是 MCP 接入的外部 AI Agent。

## 它是什么，不是什么

- 是：一个通用的定时作业运行器 + 运行历史 + 告警邮件。DailyNews 之类的程序只是其中一个普通作业，Agent 里没有任何新闻专用代码。
- 是：只在服务器本机的 Unix socket 上听命令，**不开任何端口**。唯一的出站连接是你配置的 SMTP 服务器和（可选的）心跳地址。
- 不是：root 后门。守护进程和所有作业都以系统用户 `panellab` 运行，它不在 sudoers 里，没有登录 shell。
- 不是：自动升级器、服务器上的网页界面、批量管理多台服务器的工具。第一版也没有“设置表单”（以后的阶段再做）。
- 不会：替你输入或保存 sudo 密码。安装和卸载的那一条 sudo 命令由你自己在终端里运行。

## 安装

前提：服务器是带 systemd 的 Linux，有 `python3`（3.9 或更新，不需要 pip），并且已在「任务工作区」添加这台服务器、确认了指纹。

1. 在侧边栏打开「服务器 Agent」，选中服务器。未安装时页面显示「这台服务器的 Agent 未安装」。
2. 点「上传安装包」。PanelLab 只把安装包上传到你 SSH 用户的主目录（例如 `~/panellab-agent-0.1.1-<校验码>/`），不执行任何东西。
3. 页面给出**一条** `sudo bash …/install.sh` 命令。点「复制命令」，或点「在终端打开」，在终端里自己运行它，sudo 密码只在终端里输入。安装脚本会：
   - 创建系统用户和组 `panellab`（不会动服务器上已有的其他账户，例如 `agent`）；
   - 把 `panellab` 加入 `adm` 组（只为读取 SSH 登录失败记录），把你的 SSH 用户加入 `panellab` 组；
   - 把程序装到 `/opt/panellab-agent/`，数据放在 `/var/lib/panellab-agent/`，配置放在 `/etc/panellab-agent/`；
   - 安装并启动 systemd 服务 `panellab-agent`（崩溃后自动重启）。
4. 运行完成后，**重新连接 SSH**（新开终端或重新登录），新加的组才会生效；然后在页面点「重新检查」。PanelLab 每次操作都会新建 SSH 连接，所以页面这边通常直接就能用。

## 升级

安装包每次都带版本号和校验码，`install.sh` 可以重复运行。无论是同一版本还是新版本，都会先“排空”——不再启动新运行，等正在跑的作业结束（最长等到各自的超时）；同一版本随后只重启服务，新版本则切换后再重启。安装脚本中途失败或被中断时，会让 Agent 退出排空状态、恢复调度。作业、运行历史、告警设置和秘密都会保留。

Agent 已安装时，点状态栏上的「升级 / 重新安装 Agent」，会打开标题为「升级 Agent」的安装面板，显示当前已安装的版本，上传后还会显示安装包的版本。之后的步骤和安装一样：点「上传安装包」，在终端里自己运行页面给出的那一条 sudo 命令，再点「重新检查」。协议版本不兼容时，页面也会直接显示这个面板。不想等排空，可以在命令末尾加 `--force`，正在运行的作业会被取消。

## 卸载

在服务器上运行安装目录里的脚本：

- `sudo bash …/install.sh --uninstall`：停止服务，删除程序和单元文件；**保留**作业、运行历史和配置，之后重新安装可以接着用。
- `sudo bash …/install.sh --uninstall --purge`：同时删除 `/var/lib/panellab-agent` 和 `/etc/panellab-agent`（包括秘密）。这一步不可恢复。

卸载同样会先排空正在运行的作业。卸载不会删除 `panellab` 用户和组。

## 定义作业

点「新建作业」。每个字段的含义：

- **作业 ID**：小写字母、数字和连字符，最长 48 个字符，例如 `news-briefing`。创建后不能修改。
- **名称**：显示名，也出现在告警邮件标题里。
- **命令（每行一个参数）**：命令**不经过 shell**，第一行是程序，之后每行一个参数，不需要引号或转义。例如：

  ```
  /usr/bin/python3
  run.py
  --mode
  send
  ```

  需要管道、`&&`、重定向或通配符时，显式写 shell：第一行 `/bin/sh`，第二行 `-c`，第三行放整条命令。
- **工作目录**：绝对路径，必须是 `panellab` 能进入的目录。作业运行时 `HOME` 也设为这个目录，`PATH` 只有 `/usr/local/bin:/usr/bin:/bin`，需要别的程序请写完整路径。
- **环境变量（明文）**：普通的键值对，页面上明文显示。**不要把 API 密钥、密码放在这里。**
- **环境变量文件（可选）**：服务器上一个文件的路径，每行 `KEY=VALUE`，支持 `export` 前缀和引号。文件必须对 `panellab` 可读。适合你已经有一份 `.env` 的程序；文件内容不经过 PanelLab。
- **秘密环境变量（只写）**：保存后只存在服务器上权限为 0600 的文件里，页面和接口只显示名字和“已设置”，PanelLab 也不保存。编辑时每个键可以选「保持不变 / 改为新值 / 删除」。三者同时出现同名变量时，优先级为：秘密环境变量 > 明文环境变量 > 环境变量文件。
- **计划**：一个或多个标准 5 字段 cron 表达式（分 时 日 月 周），加一个时区，例如 `20 23 * * *` + `Asia/Shanghai`。表单旁边显示“接下来 3 次运行时间”，由服务器上的 Agent 计算，所见即所得。不填计划就是“仅手动运行”。
- **超时（秒）**：默认 3600。超时后先向整个进程组发 SIGTERM，30 秒后发 SIGKILL，本次记为 `timed_out`。
- **失败重试次数 / 重试间隔（秒）**：`failed` 和 `timed_out` 会按设置重试；你手动取消的运行（`cancelled`）不会重试。告警只看重试用尽后的最后一次。
- **补跑窗口（分钟）**：默认 60。Agent 停机或服务器重启期间错过的运行：
  - 计划时间在窗口以内的，恢复后**合并成一次**补跑，记为 `catch_up`，记录和邮件里写明迟到多少分钟；
  - 超出窗口的，每个错过的时间点记一条 `missed` 并发邮件告诉你“没跑”，**不会**迟到很久再补发一份过时的内容；
  - 设为 0 表示从不补跑。
- **重叠**：上一次还没结束又到点时，这一次直接跳过，记为 `skipped_overlap`，不排队。
- **告警**：失败时通知、恢复时通知、通知附带输出（最近 20 行）。输出可能含敏感内容，不想让它进邮箱就关掉“附带输出”。

作业详情里可以「立即运行」「暂停 / 继续运行」「编辑」「删除」，正在运行的可以「取消正在运行」；运行历史可按状态筛选，点开一次运行查看完整输出（单次上限 10 MiB），正在运行的可以「跟随」。每个作业保留最近 200 次或 90 天的记录，取较多者。删除作业后，它的 ID 可以重新使用，新作业从空的运行历史开始。运行被信号结束时，退出码显示为「信号 15」这样的形式。

## 告警

在「告警设置」里填写 SMTP（主机、端口、安全方式 STARTTLS / SSL / 无、用户名、密码、发件人、最多 10 个收件人），先保存，再点「发送测试邮件」确认能收到。SMTP 密码只保存在服务器上，页面只显示“已设置”。

| 告警 | 什么时候发 | 什么时候算恢复 |
| --- | --- | --- |
| 作业失败 / 超时 | 重试用尽后最后一次仍失败或超时；Agent 意外崩溃中断的运行（`agent_lost`）也算 | 之后有一次成功 |
| 作业错过计划 | 计划时间过去仍没能开始、又超出补跑窗口 | 之后有一次成功 |
| 磁盘 | 任一真实文件系统使用率达到 90%（可调） | 回落到恢复线以下（默认 85%）；挂载点消失也算恢复 |
| CPU / 内存 | 每 30 秒采样，连续 10 分钟每次都达到 95%（可调） | 连续 5 分钟低于恢复线（默认 90%） |
| SSH 登录失败 | 10 分钟内 sshd 认证失败达到 30 次（可调），信中列出次数最多的 5 个 IP；只告警不封禁 | 回落到阈值以下 |
| Agent 曾停止运行 | Agent 重新启动时发现自己停了 5 分钟以上 | —（只发一次，说明停机时段） |

同一个问题持续时不会重复发信：状态从正常变为触发时发一封，恢复时发一封「已恢复」（触发时没有发信的，例如作业关掉了“失败时通知”，恢复时也不发）；持续触发超过 24 小时，每天最多再提醒一次。Agent 会记下最后一次发信的结果。最近一次告警邮件没发出去时，状态栏下方显示「最近一次告警邮件发送失败：…」，带上原因和时间，旁边的按钮可以直接打开告警设置。还没配置邮件时，页面显示「尚未配置告警邮件」。配置好之后，先发一封测试邮件确认能收到。

阈值留空就用默认值。恢复线为触发线减 5 个百分点（或默认值，取较低者）：例如把磁盘阈值调到 80%，就要回落到 75% 以下才算恢复，避免在阈值附近反复告警。Agent 重启后，之前触发中的磁盘、CPU、内存告警会接着判断是否恢复。SSH 登录失败告警可以在设置里关掉。

### 心跳服务：唯一能发现“整台服务器挂了”的办法

服务器宕机、断网或被关机时，服务器上的 Agent 自己发不出任何邮件。要覆盖这种情况，需要一个外部的心跳服务：

1. 在任意心跳监控服务（例如 healthchecks.io 或同类服务）新建一个检查，周期设为 5 分钟，宽限期按你的容忍度设置（例如 10 分钟），并在那边配好你的邮箱。
2. 把它给出的 ping 地址（必须是 `https://` 开头）填到「心跳 URL」并保存。
3. Agent 每 5 分钟访问一次这个地址。超过宽限期没收到，心跳服务就会给你发信。

不填心跳 URL，Agent 就不发出任何这类请求。最近一次心跳请求失败时，状态栏显示「心跳请求失败（时间）」。

## 权限说明

- 所有作业都以 `panellab` 用户运行，它不能 sudo。作业要读写的目录和文件，需要你事先给 `panellab` 相应权限。
- **能定义作业，就等于能在这台服务器上以 `panellab` 身份执行任意命令。** 能这样做的人，是能通过固定指纹 SSH 登录、并且在 `panellab` 组里的人，这和“能 SSH 就能执行命令”的现状等价。不要把别人的 SSH 用户加入 `panellab` 组。
- MCP 工具不能修改作业。

## 出问题时

| 页面提示 / 错误码 | 原因与处理 |
| --- | --- |
| `agent_not_installed` | 这台服务器上没有 `panellab-agentctl`。按“安装”一节上传并运行命令。 |
| `agent_permission` | 你的 SSH 用户还不在 `panellab` 组里，或者组权限还没生效。重新登录 SSH 后再试；用 `id` 确认输出里有 `panellab`，没有就重新运行安装命令。 |
| `agent_unreachable` | 连不上 Agent 的 socket，多半是服务没在运行。在服务器上运行 `sudo systemctl status panellab-agent` 和 `sudo journalctl -u panellab-agent -n 50` 查看原因，`sudo systemctl restart panellab-agent` 重启。 |
| 状态栏显示「正在排空」，或操作报 `draining` | 有一次升级或卸载在等待作业结束，期间不启动新运行。排空由安装脚本持续续期：脚本失败时会立即恢复调度；脚本被强行中断时，Agent 在 30 秒内自动退出排空并发一封「Agent 已退出排空状态」通知。也可以在服务器上运行 `panellab-agentctl undrain` 立即恢复。 |
| 用 `systemctl restart` / `stop` 或重启服务器时有作业在运行 | Agent 停止调度，给正在运行的作业最多 60 秒自行结束，之后中断剩下的（记为「已取消」，输出末尾有 `[Agent 停止，作业被中断]`，不发失败告警），并发一封「Agent 停止时中断了作业」通知列出它们。计划内的升级请用本页的升级入口或 `install.sh`，它们会先等作业结束。 |
| 协议版本不一致 | 面板和服务器上的 Agent 版本不匹配。页面会显示「上传安装包」，按提示重新安装即可，数据保留。 |
| 作业一启动就失败，提示“无法读取环境变量文件” | 该文件对 `panellab` 不可读，检查文件和上级目录的权限。 |
| 测试邮件失败 | 页面会显示原因（认证失败、连接失败等），检查 SMTP 主机、端口、安全方式和密码。很多邮箱需要单独的“授权码”而不是登录密码。 |

## 示例：把旧 DailyNews 迁到 Agent

现状（2026-11-10 的服务器）：账户 `newsbot` 下有两个 systemd 用户定时器，23:20、23:40、23:50 准备，00:00 发送（Asia/Shanghai）；代码在 `/srv/news-briefing`，配置在 `~newsbot/.config/news-briefing/env`。下面的步骤由你在服务器上自己完成；PanelLab 不会改动旧 DailyNews。这里迁移的是**现有程序**，新版 DailyNews（第三阶段）还不存在。

1. **看清旧作业实际运行什么。** 先以 `newsbot` 身份列出实际存在的定时器，不要假设单元名：

   ```bash
   sudo -u newsbot XDG_RUNTIME_DIR=/run/user/$(id -u newsbot) systemctl --user list-timers --all
   ```

   输出的 `UNIT` 和 `ACTIVATES` 两列是定时器和它触发的服务。再查看这些服务的命令和目录（下面以 `news-briefing-prepare.service`、`news-briefing.service` 为例，换成你看到的名字；后面各步同样替换）：

   ```bash
   sudo -u newsbot XDG_RUNTIME_DIR=/run/user/$(id -u newsbot) systemctl --user cat news-briefing-prepare.service news-briefing.service
   ```

   记下每个服务的 `ExecStart`、`WorkingDirectory` 和 `EnvironmentFile`。

2. **让 `panellab` 能读代码、能写它需要写的地方。** 二选一，**推荐另行部署**：
   - 另行部署（推荐）：复制一份到新目录，例如 `sudo cp -a /srv/news-briefing /srv/news-briefing-agent && sudo chown -R panellab:panellab /srv/news-briefing-agent`。两份互不影响，旧定时器的权限不变，回退也简单；但程序如果有自己的状态文件（例如“已发送”记录），两份不会共享。
   - 原地使用：把 `/srv/news-briefing` 的组改为 `panellab` 并给组读权限（`sudo chgrp -R panellab /srv/news-briefing && sudo chmod -R g+rX /srv/news-briefing`），程序需要写入的子目录（输出、缓存、状态文件等）再给组写权限 `g+w`。这会改动旧部署的权限，旧定时器仍以 `newsbot` 运行，改之前确认它还能正常读写。

   如果程序用到虚拟环境，命令第一行写虚拟环境里的 python 的完整路径，并确认 `panellab` 能读整个虚拟环境。

3. **处理配置文件。** 推荐复制一份给 `panellab`，而不是开放 `newsbot` 的主目录：

   ```bash
   sudo install -o panellab -g panellab -m 0600 ~newsbot/.config/news-briefing/env /etc/panellab-agent/news-briefing.env
   ```

   然后在作业的「环境变量文件」里填 `/etc/panellab-agent/news-briefing.env`。注意 `--uninstall --purge` 会连同这个目录一起删除。也可以把其中的 API 密钥、SMTP 密码等逐个填到「秘密环境变量」里，不再使用文件。

4. **在 PanelLab 中新建两个作业**（命令按第 1 步看到的 `ExecStart` 填，每行一个参数）：

   | 字段 | 准备作业 | 发送作业 |
   | --- | --- | --- |
   | 作业 ID | `news-briefing-prepare` | `news-briefing` |
   | 名称 | 早报准备 | 早报发送 |
   | 计划 | `20 23 * * *`、`40 23 * * *`、`50 23 * * *` | **先留空**（仅手动），切换时再填 `0 0 * * *` |
   | 时区 | `Asia/Shanghai` | `Asia/Shanghai` |
   | 工作目录 | 第 2 步的代码目录 | 同左 |
   | 环境变量文件 | `/etc/panellab-agent/news-briefing.env` | 同左 |
   | 超时 | 按准备通常耗时留余量，例如 900 秒 | 例如 600 秒 |

   发送作业的补跑窗口保持默认 60 分钟即可：服务器在 00:00 前后短暂不可用时 01:00 前还会补发，再晚就记为“错过”并发邮件告诉你，而不是早上 9 点再发一份旧闻。旧定时器的 `Persistent=true` 没有这个上限，这一点是有意的改变。

5. **先在新作业上测试，不让它发出真实邮件。** 发送作业创建时计划留空，它就不会按时运行，不会和旧的发送定时器同时发信。对准备作业点「立即运行」，查看输出确认能正常运行。发送作业如果程序有试运行或只发给自己的选项，用它测试一次；否则等到第 6 步再让它真正运行。

   试运行期间新旧两个准备作业会各自按时运行。只有程序能容忍两次准备同时或先后进行（例如不会争用同一个输出文件）时，这样才安全；拿不准就先「暂停」新的准备作业，等第 6 步停掉旧定时器后再「继续运行」。

6. **切换，不要让两边同时发信。** 两套定时器同时启用，你会在 00:00 收到两份早报。建议在某天 00:00 之前：
   1. 先停掉旧的**发送**定时器：

      ```bash
      sudo -u newsbot XDG_RUNTIME_DIR=/run/user/$(id -u newsbot) systemctl --user disable --now news-briefing.timer
      ```

   2. 在 PanelLab 里编辑 `news-briefing`，把计划填为 `0 0 * * *`（时区 `Asia/Shanghai`）并保存。
   3. 次日确认 PanelLab 的运行历史里两个作业都成功、你也收到了早报。
   4. 新作业至少成功运行一次之后，再停掉旧的**准备**定时器：

      ```bash
      sudo -u newsbot XDG_RUNTIME_DIR=/run/user/$(id -u newsbot) systemctl --user disable --now news-briefing-prepare.timer
      ```

   新作业失败时，重新启用旧定时器（把 `disable --now` 换成 `enable --now`）并在 PanelLab 暂停新作业，即可回到原样。如果第 5 步暂停了新的准备作业，停掉旧的准备定时器后记得对它点「继续运行」。旧的代码、配置和定时器文件都不用删除。
