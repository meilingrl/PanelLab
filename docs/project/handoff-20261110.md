**用户真正想解决的问题**

用户最初授权自主挖掘产品价值，寻找一到几个值得深入打磨的锚点。项目已有基本面板功能，但用户觉得功能广度、深度都缺少吸引力，连自己也缺少日常打开它的动力。目标是做出自己平时愿意用的工具，而不是把面板功能列表继续扩长。

具体痛点包括不愿使用宝塔一类复杂面板，不愿使用卡顿、输入不便的云厂商终端，不愿自己记 SSH 命令；Agent 可以代做操作，但没有 Agent 时仍希望能自己完成常见工作。Tabby 一类终端改善了连接体验，却仍要求技术知识、手打路径和额外查状态。用户也关心服务器流量管理的便利程度。

实际场景主要是模型训练实验、网站、每日早报一类定时任务，下载和传输频率较低但有价值。用户很少在服务器上开发，Docker 工作负载管理也不是其高频需求。本轮使用 Docker 简化面板本地运行，是交付方式的选择。

最初做过“可审查、可恢复的 Nginx 站点变更”。用户认为有收益，但不足以成为最值得讲的功能。因此后续主线转为“把已有任务的服务器、进程、目录、日志和结果关联起来，让人和外部 Agent 回到同一个任务”。这是已实现并等待日常试用的产品假设，尚无用户留存或独有性证据。

用户主动提出借鉴 Tailscale，让人和 AI 共同使用一个软件，也问过陌生 Agent 如何接入。已形成的实现选择是共享任务 ID、API、CLI 和可选 MCP。当前 Agent 指外部客户端中的 Agent；项目没有内置大模型聊天或自主执行循环。Tailscale 是可选连接方式，实际 tailnet、Tailscale SSH/check-mode 尚未验收。历史竞品调查仅反映当时资料，不能把“支持 Agent”直接当作独创性依据。

**项目结构、入口与开发环境**

后端为 Python/FastAPI、SQLAlchemy/MySQL、Paramiko，前端为 Vue 3、Vite、xterm.js、Vitest。测试用 SQLite 只用于指定测试场景。远程观测目标为 Linux/Python 3，终端目录操作要求 POSIX 兼容 shell。可选 MCP SDK 固定为 mcp==2.3.0，放在独立环境。

源码位置均相对于上述 reliability 工作区。

- backend/routers/workloads.py、backend/services/workloads.py 负责任务及有界文件读取；backend/services/remote_* 负责连接、采集、文件和票据。
- frontend/src/views/dashboard/Workspaces.vue 与 frontend/src/components/workspaces/ 为任务界面；useBoundTaskRead.js 共用观测/日志调度，useTaskObservation.js 处理观测，observationRates.js 计算区间值。改共享调度时需要考虑两种调用者。
- backend/services/site_changes.py、nginx_manager.py 和相应路由负责站点变更。backend/routers/monitor.py 是需单独理解的旧监控入口。
- scripts/panellab.py 为标准库 CLI，panellab_mcp.py 为模式/配置入口，panellab_mcp_server.py 为 MCP 工具。
- scripts/local_panel.py 和 compose.local.yaml 为新本地入口。旧 docker-compose.yml 仍为固定口令演示配置。
- 新启动器默认 Web 端口 8765，直接开发的后端通常为 8000，Vite 通常为 5173。连接应使用实际启动输出；MCP 的 --url 可显式指定。
