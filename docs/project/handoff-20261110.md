**The problems the user wants to solve**

The user originally authorized independent exploration of the product's value, seeking one or a few compelling areas to develop in depth. The project already had basic panel functionality, but the user found neither its breadth nor its depth sufficiently appealing, and had little motivation to open it regularly themselves. The goal is a tool they would willingly use in everyday work, rather than an ever-longer list of panel features.

Specific frustrations include reluctance to use complex panels such as BaoTa, cloud-provider terminals with lag and awkward input, and SSH workflows that require remembering commands. An Agent can perform operations on the user's behalf, but the user still wants to handle common work independently when no Agent is available. Terminals such as Tabby improve connection handling while still requiring technical knowledge, manually entered paths, and separate status checks. The user also wants more convenient server traffic management.

The main use cases are model-training experiments, websites, and scheduled jobs such as a daily news briefing. Downloads and transfers are less frequent but still valuable. The user rarely develops directly on servers, and Docker workload management is not a frequent need. Using Docker to simplify local panel startup in this iteration was a delivery choice.

The first improvement was reviewable, recoverable Nginx site configuration changes. The user saw value in it but felt it was insufficient as the product's strongest reason to use it. The subsequent focus became associating an existing task with its server, process, directory, logs, and results, so that a person and an external Agent can return to the same task. This product hypothesis has been implemented and awaits everyday use. There is no evidence yet of user retention or uniqueness.

The user proposed learning from Tailscale so that people and AI could use the same software, and asked how an Agent unfamiliar with PanelLab could connect. The implemented approach uses shared task IDs, an API, a CLI, and optional MCP. Here, Agent means an Agent in an external client. The project has no built-in LLM chat or autonomous execution loop. Tailscale is an optional connection method. Actual tailnet, Tailscale SSH, and check-mode behavior have not been accepted through testing. Historical competitor research reflects the information available at that time, and Agent support alone should not be treated as evidence of originality.

Two integration gaps were specifically confirmed in the source during this handoff.

- Legacy monitoring connections in backend/routers/monitor.py still use Paramiko AutoAddPolicy, and retain separate remote-config and remote psutil-installation endpoints. The new workspace and terminal host-key pinning mechanism does not cover those legacy endpoints. Assessing SSH behavior across the application requires checking the actual call path.
- Database setup still primarily relies on create_all. Site-audit TEXT columns created by early branches will not automatically become the current model's MySQL MEDIUMTEXT columns. A complete migration and upgrade workflow has not been delivered. The new GUI, CLI, and MCP use /api/workloads/{id}/log. Check server and client versions when updating, since an older backend cannot serve that new endpoint.

Account handling and production use have additional existing boundaries. INIT_ADMIN_PASSWORD creates a user only during initial database setup, and changing the configuration does not reset an existing password. JWTs expire after seven days by default, and signing in again or deleting a token file cannot revoke an older token. Nginx/MySQL administration is intended for trusted operator accounts and still uses shared services configured for the panel. TLS, backup and restore, complete dependency locking, multi-instance strategy, and failure recovery need validation for the intended deployment. The default image does not install Nginx, and site management inside a container does not automatically operate on the host's Nginx.

**Project structure, entry points, and development environment**

The backend uses Python/FastAPI, SQLAlchemy/MySQL, and Paramiko. The frontend uses Vue 3, Vite, xterm.js, and Vitest. SQLite is used only in designated test scenarios. Remote observation targets Linux/Python 3, and terminal directory operations require a POSIX-compatible shell. The optional MCP SDK is pinned to mcp==2.3.0 in a separate environment.

Source locations below are relative to the reliability worktree described above.

- backend/routers/workloads.py and backend/services/workloads.py handle tasks and bounded file reads. backend/services/remote_* handles connections, collection, files, and tickets.
- frontend/src/views/dashboard/Workspaces.vue and frontend/src/components/workspaces/ implement the task UI. useBoundTaskRead.js shares observation/log scheduling, useTaskObservation.js handles observation, and observationRates.js calculates interval values. Changes to the shared scheduler need to account for both callers.
- backend/services/site_changes.py, nginx_manager.py, and their routes handle site changes. backend/routers/monitor.py is the legacy monitoring entry point that needs separate consideration.
- scripts/panellab.py is the standard-library CLI, panellab_mcp.py handles modes and configuration, and panellab_mcp_server.py provides the MCP tools.
- scripts/local_panel.py and compose.local.yaml are the new local entry points. The older docker-compose.yml remains a demonstration configuration with fixed passwords.
- The new launcher's default web port is 8765. A backend started directly for development usually uses 8000, and Vite usually uses 5173. Use the actual startup output for connection addresses. MCP accepts an explicit --url.
- A local instance stores data/local-panel/panellab-local.json, with its database in the corresponding Docker named volume. Both the credential file and database are needed for recovery. SECRET_KEY is used for signing and for decrypting stored SSH passwords.
